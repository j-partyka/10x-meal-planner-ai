# REST API Plan

## 1. Resources

| Resource      | Database table / source | Description |
|---------------|--------------------------|-------------|
| **Products**  | `public.products`       | Kitchen inventory items. One row per product; owned by user via `user_id`. |
| **Meal plan** | — (computed)             | Weekly meal plan (7 days × breakfast/lunch/dinner). Generated by AI; not persisted. |
| **Shopping list** | — (computed)         | Missing ingredients for the meal plan, grouped by category. Derived from meal plan and inventory. |

**Note:** `product_unit` is an enum (`kg`, `g`, `ml`, `L`, `pieces`) used by the Products resource. There are no `meal_plans` or `shopping_list` tables; both are produced in application logic.

---

## 2. Endpoints

### 2.1 Products

#### List products

- **Method:** `GET`
- **Path:** `/api/products`
- **Description:** Returns the authenticated user’s products with optional search, filtering, sorting, and pagination.
- **Query parameters:**

| Parameter | Type   | Required | Default | Description |
|-----------|--------|----------|---------|-------------|
| `search`  | string | No       | —       | Case-insensitive search in `name` and `category`. |
| `category`| string | No       | —       | Filter by exact or partial category. |
| `sort`    | string | No       | `expiration_date` | Sort field: `name`, `expiration_date`, `created_at`, `quantity`, `category`. |
| `order`   | string | No       | `asc`   | Sort order: `asc` or `desc`. |
| `page`    | number | No       | `1`     | Page number (1-based). |
| **limit** | number | No       | `50`    | Items per page (max `100`). |

- **Request body:** None.
- **Response (200):**

```json
{
  "data": [
    {
      "id": "uuid",
      "user_id": "uuid",
      "name": "string",
      "quantity": 123.456,
      "unit": "kg",
      "expiration_date": "YYYY-MM-DD",
      "category": "string | null",
      "created_at": "ISO8601"
    }
  ],
  "meta": {
    "total": 42,
    "page": 1,
    "limit": 50,
    "totalPages": 1
  }
}
```

- **Success:** `200 OK` — List and pagination meta returned.
- **Errors:** `401 Unauthorized` — Not authenticated. `500 Internal Server Error` — Server or database error.

#### Get product by ID

- **Method:** `GET`
- **Path:** `/api/products/:id`
- **Description:** Returns a single product by ID. User can only access their own product.
- **Query parameters:** None.
- **Path parameters:** `id` — Product UUID.
- **Request body:** None.
- **Response (200):**

```json
{
  "id": "uuid",
  "user_id": "uuid",
  "name": "string",
  "quantity": 123.456,
  "unit": "kg",
  "expiration_date": "YYYY-MM-DD",
  "category": "string | null",
  "created_at": "ISO8601"
}
```

- **Success:** `200 OK` — Product returned.
- **Errors:** `401 Unauthorized` — Not authenticated. `404 Not Found` — Product not found or not owned by user. `500 Internal Server Error` — Server error.

---

#### Create product

- **Method:** `POST`
- **Path:** `/api/products`
- **Description:** Creates a new product for the authenticated user. `user_id` is set server-side from the session.
- **Request body:**

```json
{
  "name": "string",
  "quantity": 123.456,
  "unit": "kg",
  "expiration_date": "YYYY-MM-DD",
  "category": "string | null"
}
```

| Field             | Type   | Required | Validation |
|-------------------|--------|----------|------------|
| `name`            | string | Yes      | Non-empty, length ≤ 200. |
| `quantity`        | number | Yes      | > 0, up to 3 decimal places. |
| `unit`            | string | Yes      | One of: `kg`, `g`, `ml`, `L`, `pieces`. |
| `expiration_date` | string | Yes      | Valid date (YYYY-MM-DD); past dates allowed. |
| `category`        | string | No       | If present, length ≤ 100. |

- **Response (201):**

```json
{
  "id": "uuid",
  "user_id": "uuid",
  "name": "string",
  "quantity": 123.456,
  "unit": "kg",
  "expiration_date": "YYYY-MM-DD",
  "category": "string | null",
  "created_at": "ISO8601"
}
```

- **Success:** `201 Created` — Product created; body is the new resource.
- **Errors:** `400 Bad Request` — Validation failed (e.g. missing required field, invalid unit, quantity ≤ 0). `401 Unauthorized` — Not authenticated. `500 Internal Server Error` — Server or database error.

---

#### Update product

- **Method:** `PATCH`
- **Path:** `/api/products/:id`
- **Description:** Updates an existing product. User can only update their own product. Partial updates supported; only provided fields are changed.
- **Path parameters:** `id` — Product UUID.
- **Request body:** Any subset of:

```json
{
  "name": "string",
  "quantity": 123.456,
  "unit": "kg",
  "expiration_date": "YYYY-MM-DD",
  "category": "string | null"
}
```

Same validation rules as create. `user_id` must not be sent; it is never updated.

- **Response (200):**

```json
{
  "id": "uuid",
  "user_id": "uuid",
  "name": "string",
  "quantity": 123.456,
  "unit": "kg",
  "expiration_date": "YYYY-MM-DD",
  "category": "string | null",
  "created_at": "ISO8601"
}
```

- **Success:** `200 OK` — Product updated; body is the updated resource.
- **Errors:** `400 Bad Request` — Validation failed. `401 Unauthorized` — Not authenticated. `404 Not Found` — Product not found or not owned by user. `500 Internal Server Error` — Server error.

---

#### Delete product

- **Method:** `DELETE`
- **Path:** `/api/products/:id`
- **Description:** Deletes a product. User can only delete their own product. Hard delete (no soft delete in MVP).
- **Path parameters:** `id` — Product UUID.
- **Request body:** None.
- **Response (204):** No body.
- **Success:** `204 No Content` — Product deleted.
- **Errors:** `401 Unauthorized` — Not authenticated. `404 Not Found` — Product not found or not owned by user. `500 Internal Server Error` — Server error.

### 2.2 Meal plan and shopping list

#### Generate meal plan and shopping list

- **Method:** `POST`
- **Path:** `/api/meal-plan`
- **Description:** Generates a weekly meal plan (7 consecutive days, breakfast/lunch/dinner per day) using AI (OpenRouter/GPT), and a shopping list of missing ingredients grouped by category. Does not persist the plan or list. Uses expiration priority (e.g. within 3 days, within 7 days) and hardcoded family profile for MVP.
- **Request body:**

```json
{
  "products": [
    {
      "id": "uuid",
      "name": "string",
      "quantity": 123.456,
      "unit": "kg",
      "expiration_date": "YYYY-MM-DD",
      "category": "string | null"
    }
  ],
  "startDate": "YYYY-MM-DD"
}
```

| Field       | Type   | Required | Description |
|------------|--------|----------|-------------|
| `products` | array  | No       | Inventory to use. If omitted, server fetches current products for the authenticated user from the database. |
| `startDate`| string | No       | First day of the 7-day plan. Default: today or next day. |

- **Response (200):**

```json
{
  "mealPlan": {
    "days": [
      {
        "date": "YYYY-MM-DD",
        "breakfast": {
          "name": "string",
          "ingredients": [
            { "name": "string", "quantity": 123.456, "unit": "string" }
          ],
          "instructions": ["string"]
        },
        "lunch": { "name": "string", "ingredients": [], "instructions": [] },
        "dinner": { "name": "string", "ingredients": [], "instructions": [] }
      }
    ]
  },
  "shoppingList": {
    "items": [
      { "name": "string", "quantity": 123.456, "unit": "string", "category": "string" }
    ],
    "grouped": {
      "categoryKey": [
        { "name": "string", "quantity": 123.456, "unit": "string", "category": "string" }
      ]
    }
  }
}
```

- **Success:** `200 OK` — Meal plan and shopping list returned.
- **Errors:** `400 Bad Request` — Invalid request (e.g. invalid `startDate`). `401 Unauthorized` — Not authenticated (required if `products` is omitted). `422 Unprocessable Entity` — Empty inventory when server fetches products. `429 Too Many Requests` — Rate limit (e.g. AI provider). `502 Bad Gateway` / `503 Service Unavailable` — AI service failure. `504 Gateway Timeout` — AI call timeout (e.g. 60s). `500 Internal Server Error` — Server error.

**Business logic (handled in this endpoint):** Expiration priority (high: ≤3 days, medium: ≤7 days); nutritional and time constraints from hardcoded family profile; leftover suggestions; aggregation of shopping list quantities; grouping by category (items without category in “Other” / “Miscellaneous”).

---

#### Compute shopping list from meal plan (optional)

- **Method:** `POST`
- **Path:** `/api/shopping-list`
- **Description:** Computes missing ingredients for a given meal plan against current user inventory. Use when the client already has a meal plan and wants an updated list after inventory changes, without regenerating the full plan.
- **Request body:**

```json
{
  "mealPlan": {
    "days": [
      {
        "date": "YYYY-MM-DD",
        "breakfast": { "name": "string", "ingredients": [], "instructions": [] },
        "lunch": { "name": "string", "ingredients": [], "instructions": [] },
        "dinner": { "name": "string", "ingredients": [], "instructions": [] }
      }
    ]
  }
}
```

- **Response (200):**

```json
{
  "items": [
    { "name": "string", "quantity": 123.456, "unit": "string", "category": "string" }
  ],
  "grouped": {
    "categoryKey": [
      { "name": "string", "quantity": 123.456, "unit": "string", "category": "string" }
    ]
  }
}
```

- **Success:** `200 OK` — Shopping list returned.
- **Errors:** `400 Bad Request` — Invalid or missing `mealPlan`. `401 Unauthorized` — Not authenticated. `500 Internal Server Error` — Server error.

## 3. Authentication and Authorization

- **Mechanism:** Supabase Auth (JWT). Clients send the Supabase session (e.g. via cookie or `Authorization: Bearer <access_token>`). Astro API routes resolve the user with the Supabase server/client and enforce that only the authenticated user’s data is used.
- **Products:** All product endpoints require an authenticated user. `user_id` is taken from `auth.uid()` (or equivalent from the validated session). RLS on `products` guarantees that only rows with `user_id = auth.uid()` are read or modified; API layer must use the same identity (e.g. anon key + user JWT, or service role with explicit `user_id` from session).
- **Meal plan / shopping list:** `POST /api/meal-plan` and `POST /api/shopping-list` require authentication when inventory is read from the database (e.g. when `products` is omitted or when recomputing list from current inventory). If the client sends a full `products` payload and the server does not need DB access, authentication can be optional for that flow; for consistency and abuse prevention, requiring auth for all meal-plan and shopping-list calls is recommended.
- **Protected routes:** Middleware (e.g. `src/middleware/index.ts`) should reject unauthenticated requests to `/api/products`, `/api/meal-plan`, and `/api/shopping-list` with `401` and a consistent error payload.
- **No RBAC in MVP:** All authenticated users have the same permissions (own data only). No roles or admin endpoints.

## 4. Validation and Business Logic

### 4.1 Products (from database schema and PRD)

- **name:** Required. Length ≤ 200 (`products_name_length`). Non-empty after trim.
- **quantity:** Required. Must be > 0 (`products_quantity_positive`). Numeric, up to 3 decimal places (NUMERIC(10,3)).
- **unit:** Required. Must be one of: `kg`, `g`, `ml`, `L`, `pieces` (enum `product_unit`).
- **expiration_date:** Required. Valid date (YYYY-MM-DD). Past dates allowed per schema and PRD.
- **category:** Optional. If present, length ≤ 100 (`products_category_length`). Can be null or empty string (normalize to null if desired).
- **user_id:** Never accepted in request body. Set server-side from authenticated user on create; immutable on update.

API layer should return `400` with a structured message (e.g. `{ "error": "Validation failed", "details": [{ "field": "quantity", "message": "Must be greater than 0" }] }`) for validation failures.

### 4.2 Meal plan and shopping list (business logic in API)

- **Expiration priority:** When building the prompt or input for AI, mark items expiring within 3 days as high priority and within 7 days as medium priority; plan should use these earlier in the week.
- **Family profile (MVP):** Hardcoded in the API: 2 adults (moderate activity), 1 child (3 years, 100 cm, 18 kg); no dietary restrictions; breakfast ≤10 min, lunch ≤15 min, dinner ≤30 min; moderate complexity.
- **Leftovers:** Prompt instructs AI to suggest leftover reuse (e.g. dinner → next day lunch) where appropriate.
- **Shopping list:** Compute ingredients required by the meal plan, subtract current inventory (by name/unit, with quantity logic), aggregate quantities per ingredient, then group by category; uncategorized items go to “Other” or “Miscellaneous”.
- **Empty inventory:** If the server fetches products and the user has no products, return `422` with a message such as “Add products to inventory first” instead of calling the AI.
- **AI failures:** Map timeouts (e.g. 60s), rate limits, and provider errors to appropriate HTTP status codes (e.g. 504, 429, 502/503) and a user-facing message (e.g. “Unable to generate meal plan. Please try again in a moment.”) without exposing internal details.

### 4.3 List endpoint (products)

- **Pagination:** Enforce a maximum `limit` (e.g. 100). Default `limit` and `page` so that responses are bounded.
- **Sort:** Allow only allowed `sort` fields to avoid injection or inefficient queries; use indexes (`products_user_id_idx`, `products_expiration_date_idx`, `products_name_idx`, `products_user_id_category_idx`) where applicable.
- **Search:** Apply case-insensitive search on `name` and `category` (e.g. `ilike`); keep response time target (e.g. &lt; 500 ms for search) in mind.

### 4.4 Security and performance (reference)

- **Rate limiting:** Consider per-user or per-IP limits on `POST /api/meal-plan` (and optionally on product mutations) to protect AI costs and abuse (PRD: “Handle rate limits gracefully”; tech stack: “Financial limits configured on API keys”).
- **API keys:** OpenRouter (and other secrets) only in server-side environment variables; never exposed to the client (tech stack: “Secure API key management”).
- **Performance:** Align with PRD/tech stack targets: inventory list load &lt; 2 s, meal plan generation &lt; 30 s, form submission &lt; 1 s, search &lt; 500 ms; use DB indexes and minimal payloads to support these.

This plan is compatible with Astro 5 API routes under `src/pages/api/`, TypeScript, and Supabase (PostgreSQL + Auth + RLS), and covers the MVP scope described in the db-plan, PRD, and tech-stack documents.
